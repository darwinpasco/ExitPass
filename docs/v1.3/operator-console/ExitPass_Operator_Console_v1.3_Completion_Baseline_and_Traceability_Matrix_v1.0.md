## 2. Conclusion and concise audit summary

The current Operator Console is **substantially implemented but not a complete or fully accepted v1.3 console**. Authentication has credible current cross-application acceptance, the statutory decision and secure evidence backend are well tested, several read-only operational surfaces exist, and the prohibited payment, payment-finality, Sales Invoice issuance, ExitAuthorization issuance, and gate-control authorities are absent. However, mandatory continuity/manual-release/post-restoration capabilities are absent, the WebPay/APT service-channel review queue is not connected to the current UI, several operational and accessibility behaviors lack current integrated acceptance, and two present behaviors conflict with the v1.3 architecture: an Operator Console Sales Invoice void mutation and display of non-PHP currency values.

This baseline contains **56 requirements**: the 33 approved `OC-FR-*` requirements plus 23 non-duplicative v1.3 contract/design controls needed to trace session lifecycle, independent permissions, channel convergence, evidence lifecycle, concurrency, failure posture, accessibility, architecture, currency, and notification scope.

The distinction between implementation and evidence is material. Existing lookup, status, health, audit, authentication/session, terminal decision, secure evidence, and authority-boundary functions should be acceptance-tested on the current baseline rather than rebuilt. The missing continuity governance, manual release, post-restoration review, privacy notice, and channel-connected reviewer experience are genuine implementation gaps.

### 3.1 Requirements authority

Only the current v1.3 documents recorded as `A01` through `A16` below were used as requirements authority. v1.2 attachments, the former Operator Console BRD v1.0, historical audit summaries, implementation notes, and runbooks were not used to add, remove, or override requirements. Historical material appears only as implementation or runtime-evidence context.

Where a broad platform statement duplicates an approved `OC-FR-*` requirement, it is traced in the corresponding `OC-FR-*` row. A supplementary row exists only when a current v1.3 contract or design adds a separately testable control. `OC-NOTIF-001` deliberately records that v1.3 requires in-product queues/status refresh, not a separate email/SMS/push notification subsystem.

## 4. Minimum usable v1.3 scope

The minimum usable Operator Console requires: current human authentication/session handling; server-enforced role, permission, Site/Site Group, device/trust, and applicable shift controls; session lookup and authoritative payment/fiscal/ExitAuthorization visibility; one converged WebPay/APT statutory review queue and detail view; secure evidence presentation; approve/reject with required attribution, reason/attestation, separation of duties, terminal-state immutability, and stale/concurrent conflict handling; auditability and safe failure behavior; the mandatory continuity, fiscal-exception, manual-release, and post-restoration governance assigned to the console; responsive accessible operation; and preservation of all Central PMS, POS Server, and HikCentral authority boundaries.

Rows marked Mandatory or Conditional mandatory are completion-blocking when applicable. Optional/deferred items are identified in Section 8 and do not expand the v1.3 baseline.

## 6. Analysis and findings

### 6.1 Accepted capabilities

The following current capabilities meet the stricter `IMPLEMENTED_AND_ACCEPTED` rule:

- Current human login, session bootstrap/current-session scope presentation, logout, and production fixture-header rejection.
- Browser secret/storage boundary: cookie-based session, in-memory CSRF state, and no client-provided identity/scope authority.
- Operator Console does not accept payment, declare payment finality, issue Sales Invoices, issue ExitAuthorization, or control gates.
- Browser integration remains behind the same-origin Central PMS facade rather than directly calling POS Server, payment providers, Vendor PMS, or HikCentral.
- The statutory reviewer is a human decision surface; the current Operator Console apply route is absent, and the console does not independently calculate entitlement or apply the payable basis.

Acceptance of these negative boundaries does not excuse the separate fiscal-void mutation conflict.

### 6.2 Implemented features lacking current integrated acceptance

The following are primarily acceptance/evidence gaps, not rebuild candidates:

- Full session expiry, revocation, permission change, 401/403, and open-workflow behavior.
- Site/Site Group enforcement across every Operator Console route and persona.
- Session detail, payment status, fiscal status, ExitAuthorization status, connector health, projection freshness, and stale-alert surfaces.
- Independent statutory approve/reject/evidence permissions and terminal decision immutability.
- Central PMS-only approved payable-basis application and ordinary-payment continuation after rejection/unavailability.
- Secure evidence lifecycle and browser privacy behavior. Backend disposable-environment evidence is credible; current headed end-to-end review remains pending.
- Existing fiscal view/audit and general audit/report surfaces.

R05 through R09 remain useful history but predate material auth, channel, evidence, or route changes. They cannot establish acceptance of the current audited tree.

### 6.3 Genuine missing or partial capabilities

- The current UI uses legacy statutory draft routes instead of the implemented WebPay/APT service-channel pending/detail/decision APIs.
- Ticket search exists, but card and plate search are not complete in the UI; card contract support was not found.
- Required privacy notice content is absent from the evidence-review experience.
- Supervisor override, reason taxonomy/notes, durable separation of duties, current concurrency token/refetch behavior, and complete cross-channel state rendering are incomplete.
- Evidence retention/deletion/hold execution is incomplete even though review access and selected lifecycle states are implemented.
- Continuity activation/deactivation, incident/BCP linkage, Continuity Terminal activation review, manual release, and post-restoration review are absent.
- Fiscal exception review is a collection of read/status/audit surfaces, not the complete governed queue/detail/escalation workflow.
- Route-complete audit, scoped export, audit-sink failure policy, dependency-wide failure/retry acceptance, operational telemetry/readiness, and whole-console accessibility acceptance are incomplete.

### 6.4 Architecture and implementation conflicts

1. `OC-ARC-003`: the current UI and Central PMS Operator Console facade implement Sales Invoice void mutation. This conflicts with the v1.3 read-only/non-fiscal Operator Console boundary and POS Server fiscal ownership. Permission checks and action audit do not transfer fiscal authority.
2. `OC-ARC-004`: `formatMoney` displays any supplied currency code and defaults a missing code to PHP. ExitPass v1.3 supports PHP only; unsupported currencies must be rejected or safely suppressed, not displayed as supported or silently relabelled.

No direct gate-control, Sales Invoice issuance, payment-processing, payment-finality, ExitAuthorization-issuance, or independent statutory-rule calculation conflict was found.

### 6.5 Mandatory minimum and classification

All rows in Sections 5.1 and 5.2 except `OC-NOTIF-001` form the mandatory minimum when applicable. The four conditional rows are `OC-FR-004`, `OC-FR-006`, `OC-FR-015`, and `OC-FR-024`; each needs an explicit approved applicability/policy decision, and each becomes completion-blocking when applicable. All other non-notification rows are mandatory. Later-phase items in Section 7.3 are not part of minimum completion.

The correct classification is `PARTIAL`, not `IMPLEMENTED_NOT_FULLY_ACCEPTED`, because the baseline contains seven `NOT_IMPLEMENTED` requirements, 22 `PARTIAL` requirements, and two active architecture conflicts. The console is not classified `NOT_READY` because current authentication, scoped foundations, read-only operational views, statutory decision/evidence services, test coverage, and several accepted boundaries are material and usable development progress.

## 7. Ordered completion backlog

### 7.1 Absolute required

These tasks contain implementation or policy work and must be executed in order where dependencies overlap.

1. **Remove the fiscal-authority conflict (`OC-ARC-003`).** Remove the Operator Console fiscal-void UI, API-client call, Central PMS Operator Console void facade, and action execution permission/wiring. Preserve read-only fiscal history/audit. Add negative route/authorization tests.
