# ExitPass POS Server API Contract Open Questions

Status: Initial API contract planning artifact only

This list reclassifies POS Server System Design open questions for API Contract impact. It does not close approved BRD/System Design decisions.

| ID | Question | Source / reason | Decision owner | Blocks API Contract? | Blocks Database Design? | Blocks implementation? | Proposed default, if safe | Risk if decided incorrectly |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| API-OQ-001 | What final endpoint route family naming should be used? | API Contract outline needs route family naming. | Architecture/API owners | Yes | No | Yes | Use clear fiscal issuance, document, presentation, registry, identity, report/export, adjustment, reset/recovery, exception/status, and audit/event families until names are finalized. | Fragmented or inconsistent API contract. |
| API-OQ-002 | What are the request/response DTO boundaries and shared metadata conventions? | Full API Contract must define payload boundaries later. | Architecture/API owners | Yes | Maybe | Yes | Keep shared context limited to Site/session/payment/channel/actor/correlation/fiscal reference concepts. | Overbroad payloads or missing required context. |
| API-OQ-003 | What is the idempotency key scope for Sales Invoice issuance? | System Design requires idempotent issuance. | Architecture, Central PMS owners, BIR/accounting | Yes | Yes | Yes | Scope idempotency to Central PMS issuance intent for a resolved Site/payment/session pending final contract. | Duplicate fiscal documents or blocked legitimate retries. |
| API-OQ-004 | How should duplicate issuance requests be handled? | Retry/timeouts require safe duplicate handling. | Architecture/API owners | Yes | Yes | Yes | Return the same fiscal identity/status for a confirmed duplicate where safe. | Duplicate SI issuance or inconsistent fiscal references. |
| API-OQ-005 | How should sequence gaps, reserved numbers, failed issuance, and abandoned issuance be represented? | PSD-OQ-018; BIR/accounting dependency. | BIR/accounting, architecture | Yes | Yes | Yes | Use explicit issuance states pending BIR signoff. | Missing or duplicate SI numbers; non-compliant audit trail. |

| API-OQ-014 | What terminal/channel registry fields are required? | System Design Section 9. | Architecture, database design, security | Yes | Yes | Yes | Include Site, channel type, identity, capability, status, fiscal metadata reference, actor/session support, and audit concepts. | Missing channel controls or over-specified registry. |

| API-OQ-016 | What X-read and Z-read scopes are approved? | PSD-OQ-007. | BIR/accounting, finance, operations | Yes | Yes | Yes | Design API to allow Site, terminal/channel, cashier/session, or combined scope pending confirmation. | X/Z reports fail reconciliation. |

| API-OQ-024 | What security/RBAC model applies to high-risk APIs? | Reprint, adjustment, reset, export, identity config, recovery are high-risk. | Security/privacy, compliance, operations | Yes | Yes | Yes | Separate cashier, supervisor, fiscal admin, compliance auditor, recovery approver, and system admin capabilities pending review. | Unauthorized fiscal actions. |

## Notes

- None of these questions reopens the approved Site-level POS Server model or Central PMS authority model.
- Open API questions should be resolved in the full API Contract, Security/Privacy Review, BIR/accounting confirmation, POS Server Database Design, and Engineering Pack workstreams.
