# ExitPass WebPay Statutory Service Authentication and Safe Error Mapping

## Purpose

This note records the bounded implementation that authenticates existing WebPay statutory-discount Payment Orchestrator calls to Central PMS and maps internal upstream authentication, authorization, configuration, and service failures to customer-safe WebPay errors.

## Trust Boundary

The browser calls only Payment Orchestrator WebPay routes:

- `POST /v1/webpay/statutory-discounts/decisions`
- `GET /v1/webpay/statutory-discounts/decisions/{statutoryDiscountDecisionCommandId}`
- `POST /v1/webpay/statutory-discounts/decisions/{statutoryDiscountDecisionCommandId}/apply-payable-basis`

Payment Orchestrator calls the shared Central PMS statutory routes:

- `POST /v1/statutory-discounts/decisions`
- `GET /v1/statutory-discounts/decisions/{statutoryDiscountDecisionCommandId}`

The WebPay browser never supplies Central PMS service credentials, service identity headers, permissions, reviewer identity, or Operator Console authority. `SourceChannel = WEBPAY` remains server-controlled business attribution and is separate from Central PMS service authentication.

## Service Authentication

Payment Orchestrator now sends the existing Central PMS RBAC service-channel headers for statutory WebPay calls from `CentralPmsWebPayClient`:

- `X-ExitPass-Service-Identity-Id`
- `X-ExitPass-Permissions`

The service identity is read from server-side configuration:

`Integrations:CentralPms:StatutoryDiscounts:WebPayServiceIdentityId`

No default production identity is embedded in source. Missing, malformed, or empty configuration fails closed before the Central PMS HTTP request is sent.

The permissions are the narrow Central PMS statutory permissions already present in `CentralPmsRbacPolicyCatalog`:

- Submit and application intent: `statutory-discounts.decision.submit.webpay`
- Durable readback: `statutory-discounts.decision.read`

These permissions satisfy the existing Central PMS named policies:

- `CentralPmsStatutoryDiscountDecisionSubmit`
- `CentralPmsStatutoryDiscountDecisionRead`

The implementation does not grant Operator Console reviewer permissions and does not use a human operator identity.

## Correlation

`X-Correlation-Id` is still accepted from the browser when valid or generated by Payment Orchestrator. Payment Orchestrator forwards the same value to Central PMS and returns a browser-safe correlation value in successful and failed statutory responses. The correlation value is not used to derive credentials.

## Safe Error Mapping

Payment Orchestrator maps statutory upstream failures before returning them to WebPay.

| Upstream condition | Browser status | Browser error code | Customer posture |
| --- | --- | --- | --- |
| Central PMS 401, 403, missing service identity config, service-channel mismatch, source-channel forbidden or ambiguous | 503 | `WEBPAY_STATUTORY_SERVICE_UNAVAILABLE` | Parking-privilege requests are temporarily unavailable. |
| Timeout, Central PMS unavailable, transient gateway failure | 503 | `WEBPAY_STATUTORY_REQUEST_TEMPORARILY_UNAVAILABLE` | Try again shortly. |
| Safe validation error | Original validation status | Original safe validation code | Review request fields and try again. |
| Safe conflict/idempotency error | Original conflict status | Original safe conflict code | Existing request/conflict behavior is preserved. |
| Unsafe or internal response wording | 502 | `WEBPAY_STATUTORY_REQUEST_FAILED` | Generic retry guidance. |

Browser responses do not include raw Central PMS response bodies, service identity ids, permission names, policy names, auth headers, stack traces, database details, backend URLs, or connection details.

## Logging and Secret Handling

Payment Orchestrator logs only operation name, safe classification, and correlation ID for statutory transport failures. It does not log request/response bodies, credentials, tokens, authorization headers, raw claims, service identity secrets, certificate data, or downstream exception text.

## Tests

Focused coverage was added for:

- statutory Central PMS client service identity and permission forwarding
- fail-closed missing service identity configuration
- source-channel remaining `WEBPAY`
- idempotency and correlation forwarding
- WebPay endpoint 401, 403, timeout/unavailable, validation, and conflict mapping
- WebPay browser-client safe messages for service-auth and transient service failures

Central PMS statutory RBAC tests remain the authority for policy enforcement and service-channel acceptance.

## Deterministic Manual Harness

Manual validation uses:

`scripts/v1.3/webpay/Invoke-WebPayStatutoryServiceAuthManualValidation.ps1`

The harness starts a local-only Central PMS statutory contract stub, Payment Orchestrator, and WebPay UI. The stub enforces the same service-channel headers used by Central PMS and records only safe request metadata in `.local/webpay-statutory-service-auth/logs`.

The harness uses the existing WebPay same-origin browser-routing model. WebPay starts with relative `/v1/webpay/...` API paths and `VITE_WEBPAY_API_PROXY_TARGET=http://127.0.0.1:5081`; `VITE_WEBPAY_API_BASE_URL` is intentionally empty. Browser requests therefore go to `http://127.0.0.1:5173/v1/webpay/...` and Vite forwards `/v1` to Payment Orchestrator. No broad or production CORS policy is introduced.

WebPay renders explicit authoritative statutory workflow states before generic retry or temporary-unavailable fallback. A durable readback with `safeErrorCode = null`, `decisionCommandStatus = AWAITING_REVIEW`, `decisionResultStatus = NOT_DECIDED`, `payableBasisReadinessStatus = AWAITING_REVIEW`, `recoveryAction = POLL_READBACK`, and `overallResultClassification = PENDING_REVIEW` is an accepted pending-review state even when `retryable = true`. In that state WebPay displays `Awaiting review`, leaves `Refresh status` available, and keeps payment unavailable while review remains active.

The `Unavailable` manual scenario isolates statutory unavailability at the statutory route. It keeps the shared Central PMS stub available for `POST /v1/vendor-parking/resolve`, so WebPay can still resolve `WEBPAY-STAT-SERVICE-AUTH-001` and display PHP 137.50 before the statutory request. The stub returns route-specific HTTP `503` only for `/v1/statutory-discounts/decisions`, and Payment Orchestrator maps it to `WEBPAY_STATUTORY_REQUEST_TEMPORARILY_UNAVAILABLE` without exposing connection-refused text, backend URLs, policy names, service headers, or raw upstream details.

For deterministic local manual validation only, WebPay accepts `webpayStatutoryRecoveryReset=1` on `localhost` or `127.0.0.1`. The parameter clears only `exitpass:webpay:statutory-discount-recovery:v1` before initial recovery load. It does not clear unrelated browser storage and does not cancel or mutate any Central PMS statutory decision.

The deterministic local WebPay service identity is:

`9b000000-0000-0000-0000-000000000005`

Source: this identity is already used by the statutory service-channel integration tests as the WebPay service identity in:

- `src/Services/CentralPms/tests/ExitPass.CentralPms.IntegrationTests/Api/StatutoryDiscountServiceChannelPostApprovalApplicationIntentApiIntegrationTests.cs`
- `src/Services/PaymentOrchestrator/tests/ExitPass.PaymentOrchestrator.UnitTests/Infrastructure/Integrations/CentralPmsWebPayClientTests.cs`

The identity is local/test-only, non-human, has only statutory submit/read posture in this harness, and carries no Operator Console reviewer, policy administration, reconciliation, or administrator authority.

The manual harness is not controlled UAT. Central PMS runtime policy acceptance remains proven by the focused Central PMS RBAC and statutory service-channel integration tests.
