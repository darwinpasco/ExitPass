## 2. Purpose and Scope

This procedure defines how an approved actor manually saves controlled Central PMS to POS Server fiscal issuance UAT evidence JSON while evidence writer implementation remains unapproved.

This closes the gap between:

- evidence writer approval record review;
- no-go decision for automatic evidence writer implementation;
- manual-save-only posture;
- controlled UAT evidence exporter;
- practical need to preserve UAT evidence safely.

The procedure explains how exported evidence JSON is saved, named, linked to approvals, checked for redaction posture, optionally hashed, assembled for review, and verified after save.

## 4. Authority Boundaries

This manual-save procedure preserves these authority boundaries:

- Central PMS owns payment finality.
- Central PMS owns fiscal reference recording.
- Central PMS owns normal ExitAuthorization.
- POS Server owns fiscal issuance and numbering only.
- POS Server response is fiscal issuance evidence only.
- POS Server does not approve payment, exit, gate opening, entitlement, manual release, or continuity.
- Manual release is not normal ExitAuthorization.
- Evidence files are audit artifacts only and do not create operational authority.

Manual evidence saving must not be interpreted as payment approval, fiscal issuance execution, ExitAuthorization issuance, gate permission, retry authorization, readback automation, or fiscal gating enforcement.

## 6. Manual-Save Posture

Current posture:

- automatic evidence writer is not approved;
- application-level writer is not approved;
- CLI writer is not approved;
- endpoint/tooling writer is not approved;
- evidence registry writer is not approved;
- manual-save-only remains in force.

Manual save is allowed only when performed by an approved actor under the controlled UAT runbook, evidence retention/governance plan, and this procedure.

Manual save does not create operational authority and does not replace the evidence writer approval record. If a future writer is desired, the approval record must be completed and approved first.

## 7. Who May Perform Manual Save

Allowed actors:

- approved UAT lead;
- approved engineering lead or delegate;
- approved evidence owner;
- approved Central PMS developer/operator acting under UAT approval.

Not allowed:

- ordinary parking operators;
- cashier-assisted terminal users;
- APM users;
- WebPay users;
- support/helpdesk without explicit approval;
- any public/API client.

The actor performing manual save must be identified in the UAT evidence template and evidence review package.

## 8. Preconditions Before Manual Save

Before manual save:

- controlled UAT run is approved;
- run ID is assigned;
- evidence owner is identified;
- approval reference is available;
- evidence export is generated by approved harness/exporter path;
- evidence export passed sensitive marker checks;
- target storage location is approved for this run or explicitly marked temporary/manual;
- redaction review owner is assigned if attachments, logs, or screenshots exist;
- no endpoint/CLI/tooling writer is used;
- no automatic file writer is used.

If any precondition fails, stop and record the issue in the UAT evidence template issues/deviations section.

## 9. Evidence Generation Source

Evidence JSON should come from the application-level evidence exporter.

Rules:

- Do not manually construct evidence JSON.
- Do not manually edit JSON content before first save.
- Do not paste raw logs into the JSON.
- Do not paste raw provider callback payloads into the JSON.
- Do not include credentials, tokens, PAN/CVV, raw entitlement evidence, unmanaged customer PII, or uncontrolled files/images.
- Save exactly what the exporter produced unless a redaction process creates a separately approved redacted copy.

The exporter output is the evidence source. Manual save is only the preservation step.

## 10. Approved Evidence Location

Because the final official evidence repository may still be unapproved, use one of two modes.

### Mode A: Official Approved Location Available

Use Mode A when an approved shared/document repository or ticket/change attachment location is available.

Rules:

- Use the approved shared/document repository or ticket/change attachment location.
- Use approved folder naming.
- Link to the run approval reference.
- Retain evidence according to the approved retention policy.
- Mark the package as official only after reviewer/signoff workflow completes.

### Mode B: Official Location Not Yet Approved

Use Mode B when no official repository is approved.

Rules:

- Do not mark evidence as official.
- Save only to a temporary controlled evidence location approved by the UAT lead or engineering lead for the run.
- Clearly mark the package as temporary/manual-save evidence.
- Track the temporary location in approval notes.
- Do not use the package as final writer-approval evidence until a repository owner approves the location.

Mode B is a continuity measure for controlled UAT evidence preservation. It is not approval for an automatic writer or permanent evidence repository.

## 11. Temporary Local Handling Rules

Temporary local copies are allowed only for transfer or redaction assembly.

Rules:

- Do not store temporary local copies inside the source repository unless an explicitly approved gitignored local dry-run mode exists.
- Do not store unredacted evidence in Downloads, Desktop, random user folders, or unmanaged sync folders.
- Do not email raw unredacted JSON if it contains sensitive context.
- Delete temporary local copies only after evidence preservation is confirmed, unless retention policy requires retention.
- If deletion is performed, record who deleted the local copy and when.
- If local copy retention is required, record the local location and retention owner.

## 12. File/Folder Naming Convention

Run ID format:

```text
CPS-POS-UAT-YYYYMMDD-<site>-<sequence>
```

Folder pattern:

```text
ExitPass-CentralPMS-PosServer-UAT/
  <environment>/
    <site-ref>/
      <yyyy-mm-dd>/
        <run-id>/
```

File names:

```text
controlled-posserver-fiscal-uat-<run-id>-evidence.json
controlled-posserver-fiscal-uat-<run-id>-review.md
controlled-posserver-fiscal-uat-<run-id>-redaction.md
controlled-posserver-fiscal-uat-<run-id>-hash.txt
```

Rules:

- Do not use arbitrary free text in file names.
- Do not include secrets, payment identifiers beyond approved references, or customer personal data in folder/file names.
- Do not overwrite existing files.
- Use supersession suffixes only under the supersession/correction procedure.

## 13. Manual Save Step-by-Step Procedure

1. Confirm controlled UAT run approval and run ID.
2. Confirm evidence owner and storage mode: Mode A official approved location, or Mode B temporary controlled location.
3. Generate evidence JSON from the controlled exporter/harness.
4. Review exporter status.
5. Confirm there is no sensitive marker rejection.
6. Create the approved folder path using the naming convention.
7. Save evidence JSON using the exact file name: `controlled-posserver-fiscal-uat-<run-id>-evidence.json`.
8. Do not overwrite an existing evidence file.
9. Create a review file or attach review notes: `controlled-posserver-fiscal-uat-<run-id>-review.md`.
10. Create a redaction note if attachments, logs, or screenshots are included: `controlled-posserver-fiscal-uat-<run-id>-redaction.md`.
11. Compute manual hash/checksum if required or recommended.
12. Record hash in `controlled-posserver-fiscal-uat-<run-id>-hash.txt` and in the review note.
13. Link evidence to ticket/change/approval reference.
14. Notify reviewers.
15. Update the UAT evidence template final outcome section.
16. Confirm no payment finality, ExitAuthorization, or gate side effect.
17. Close or escalate issues.

## 14. Sensitive Data and Redaction Check

Before sharing or attaching evidence, manually confirm the saved evidence excludes:

- PAN;
- CVV;
- tokens;
- credentials;
- secrets;
- raw provider callback payloads;
- raw entitlement evidence;
- uncontrolled images/files;
- unmanaged customer PII;
- free-form sensitive blobs.

If sensitive data is detected:

1. Stop distribution.
2. Restrict access to the current evidence package.
3. Do not attach the package to broader tickets or shared locations.
4. Notify the redaction owner.
5. Create a redacted copy only after approval.
6. Record incident/deviation in the UAT evidence template.
7. Mark evidence status as `redaction_required` or `rejected`, as applicable.

## 15. Manual Checksum/Hash Procedure

If SHA-256 is available, compute the hash with PowerShell:

```powershell
Get-FileHash -Algorithm SHA256 "<path-to-evidence.json>"
```

Record:

- algorithm;
- hash value;
- file name;
- run ID;
- timestamp;
- computed by;
- tool/command used.

Suggested hash file format:

```text
runId: CPS-POS-UAT-YYYYMMDD-<site>-<sequence>
file: controlled-posserver-fiscal-uat-<run-id>-evidence.json
algorithm: SHA-256
hash: <hash-value>
computedAt: <timestamp>
computedBy: <name/ref>
tool: Get-FileHash -Algorithm SHA256
```

If hash cannot be computed:

- mark evidence hash incomplete;
- do not mark evidence approved;
- escalate to the evidence owner;
- record the failure in the review notes.

## 16. Ticket/Change/Approval Linkage

Link the evidence package to:

- run approval reference;
- change/ticket reference;
- UAT evidence template instance;
- controlled UAT operator runbook checklist;
- this manual-save procedure;
- reviewer signoff record;
- redaction record, if any;
- hash file/reference.

The evidence package is incomplete if it cannot be traced to approval and review references.

## 17. Evidence Review Package Assembly

The review package should include:

- evidence JSON;
- hash file, if used;
- review notes;
- UAT evidence template instance;
- redaction note, if applicable;
- screenshots/logs only if redacted and approved;
- approval references;
- final outcome.

Do not attach unredacted raw logs/screenshots to broadly visible locations.

## 18. Reviewer/Signoff Procedure

Required reviewers:

- UAT lead;
- engineering lead;
- POS Server owner, if POS Server evidence was produced;
- Central PMS owner;
- operations lead, if an operational environment was used;
- compliance/accounting observer if a fiscal number was allocated.

Each reviewer should record:

- decision;
- date/time;
- evidence reference;
- hash reference;
- notes.

Reviewer signoff must confirm the evidence package does not show payment finality mutation, ExitAuthorization issuance, or gate behavior caused by the diagnostic/manual-save path.

## 19. Failure/Abort Procedure

Abort manual save if:

- run ID is missing;
- approval reference is missing;
- evidence owner is missing;
- evidence exporter reports sensitive metadata;
- output location is unknown or unapproved;
- target file exists;
- hash cannot be computed when hash is required;
- redaction owner is unavailable when needed;
- evidence implies payment/exit/gate side effect;
- evidence is manually altered without supersession record.

Abort result:

- preserve the original exporter output only if safe to do so;
- restrict access if sensitive content may exist;
- record issue/deviation;
- notify evidence owner and UAT lead;
- do not mark evidence approved.

## 20. Supersession/Correction Procedure

If correction is needed:

- do not edit approved evidence in place;
- create a replacement file with a revision suffix;
- keep the original file;
- record supersession reason;
- record supersession approver;
- hash the replacement file separately;
- link original and replacement.

Revision suffix examples:

```text
controlled-posserver-fiscal-uat-<run-id>-evidence-r02.json
controlled-posserver-fiscal-uat-<run-id>-review-r02.md
controlled-posserver-fiscal-uat-<run-id>-redaction-r02.md
controlled-posserver-fiscal-uat-<run-id>-hash-r02.txt
```

Superseded evidence remains retained unless a separately approved retention process says otherwise.

## 21. Cleanup Procedure

After save:

- confirm evidence exists in target location;
- confirm hash file exists if used;
- confirm reviewers are notified;
- confirm temporary local copies are handled according to policy;
- confirm diagnostic flags are disabled after the UAT run if applicable;
- confirm no file is saved in the source repository unless approved local dry-run mode exists;
- confirm no payment/exit/gate side effects occurred.

Cleanup must not delete fiscal reference records, payment finality records, POS Server fiscal documents, or fiscal sequence evidence.

## 22. Access Control Reminders

Access reminders:

- only approved UAT, engineering, and evidence owners may access raw evidence;
- redacted evidence may be shared only after redaction signoff;
- ordinary parking operators have no raw evidence access;
- support/helpdesk receives only approved summaries unless explicitly approved;
- unredacted evidence must stay in restricted storage;
- temporary local copies must be controlled and removed or retained according to policy.

## 24. Risks and Open Questions

Risks:

- manual save can be inconsistent if actors skip naming/linkage steps;
- Mode B temporary locations may be mistaken for official evidence;
- hash may be omitted if not required by the run;
- redaction may be delayed if attachments are included;
- local temporary copies may remain longer than intended;
- manually saved evidence may become disconnected from ticket/change approvals.

Open questions:

- final official evidence repository owner;
- final official evidence location;
- required hash/signature posture for all UAT runs;
- whether Mode B temporary evidence can be promoted after repository approval;
- exact retention period for fiscal-number allocated evidence;
- final redaction owner and SLA.
